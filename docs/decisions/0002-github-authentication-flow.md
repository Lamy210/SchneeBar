# ADR-0002: Keep local-first GitHub Device Flow with explicit anti-phishing controls

- Status: Accepted
- Date: 2026-09-24

## Context

SchneeBar is a native macOS public client. It intentionally has no mandatory cloud backend and must never embed a GitHub App private key or client secret in the app bundle or repository.

GitHub's current guidance prefers Authorization Code + PKCE over Device Flow for public clients when a web flow is practical because Device Flow can be abused for remote phishing. GitHub also documents Device Flow for desktop/headless-style GitHub App clients, including GitHub Enterprise Server.

Moving hosted GitHub authentication to PKCE without shipping a client secret would require a token-exchange backend. That would add an always-sensitive backend dependency, operational availability requirements, secret custody, and a new privacy/trust boundary that SchneeBar does not otherwise need.

GHES compatibility must also remain explicit rather than assuming hosted-GitHub authentication behavior.

## Decision

Keep the existing GitHub App Device Flow for GitHub.com, GHE.com, and supported GHES connections.

Do not add or embed a GitHub App client secret.

Do not add an authentication broker solely to replace Device Flow at this stage.

Strengthen Device Flow UX instead:

- show the exact trusted GitHub host for the authorization page;
- tell users to authorize only a code generated by the flow they just started in SchneeBar;
- tell users not to approve device codes received through chat, email, tickets, or another application;
- keep the one-time code and verification URL visible and selectable;
- continue validating the verification URL origin against the resolved GitHub endpoint before it reaches UI;
- continue respecting GitHub's polling interval and `slow_down` response;
- preserve account-identity validation before replacing Keychain credentials.

The same guidance applies to initial connection and reauthentication.

## Consequences

Positive:

- preserves local-first operation and avoids introducing a credential broker;
- no new secret is shipped to users or stored in the repository;
- GHES remains compatible with the already-supported flow;
- the primary Device Flow phishing risk is made explicit at the moment of authorization.

Costs:

- Device Flow retains an inherent remote-phishing risk that PKCE avoids;
- users must verify the host and that they initiated the flow;
- a future hosted PKCE migration would require a separately reviewed broker architecture.

## Revisit when

Re-evaluate this decision if GitHub supports a public-client GitHub App PKCE token exchange that does not require a reusable client secret, or if SchneeBar intentionally adopts a mandatory backend for other product reasons.
