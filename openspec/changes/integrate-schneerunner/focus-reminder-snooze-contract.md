# E3e draft: persisted one-time snooze per regular occurrence

Based on merged #447. A successful regular claim consumes the occurrence, records its cursor and opens one snooze opportunity identified by the original claim ticket ID and claim time. Only a currently enabled native reminder may consume this opportunity. Proposed bounds: one snooze per regular occurrence, a 60–3600 second finite delay, requested no earlier than the claim and at most 3600 seconds after it. Validate the resulting absolute deadline and delay. The caller must distinguish claim from actual notification delivery and present the action only for an appropriate alert. This is not a receipt or proof of user interaction.

A snooze has an independent UUID, original occurrence, request time and absolute deadline. It does not move the ordinary recurrence cursor, and replanning the regular schedule does not shift the snooze deadline. Claim at or after that deadline consumes the snooze once; it does not reopen another snooze opportunity. The next regular claim supersedes any outstanding previous snooze. Disabling, deleting or replacing the rule revokes relevant snooze state. A canonical no-op edit or rename preserves it. Imported data remains notification-inactive. Time-zone changes do not shift the snooze's absolute deadline. Manual clock rollback can delay eligibility/consumption; expired pending snoozes may be claimed late unless superseded, so the future coordinator must specify a missed-delivery policy.

Nested reminder state uses version 2. Version 1 remains readable with no snooze fields/opportunity; version 2 is written on changes. Reject version 1 with nonempty snooze fields, invalid/foreign occurrence, disabled/imported snooze state, inconsistent opportunity/ticket coexistence and invalid duration/date. Older binaries reject version 2; rollback to an older binary requires an explicit compatibility decision and backup, not silently discarding snooze state. Collection envelope remains version 1. Existing store limits and single-owner assumptions unchanged. No legacy migration or OS side effects. Both individual and collection stores commit before returning a separate claimedSnooze result. Atomic replacement is not fsync/power-loss durability or cross-process exclusion.

Five added regression tests cover restart, one-time consumption/early rejection, ordinary recurrence isolation and supersession, duration/action-window validation and disable, precommit failure and rule replacement, and v1/v2 compatibility/invalid records. Linux Swift 6.2.1 standalone domain smoke compiled the exact repository FocusReminderState and FocusReminderSchedule blobs (57cc1d0c0455e5b5afa0a176d68328c58af39ad9 and 10ec08a86ec714b2d7bbee02094597777237453a). Verified v1 decode, v2 roundtrip, stale/early rejection, snooze consumption, recurrence supersession and disable. Mutation omitting snooze clearing after consumption failed a precondition; normal executable passed again. This is not execution of the five new Swift Testing tests or validation of the full persistence target. Native CI required. No shipping UI, notification adapter, outbox, OS cancellation, durable delivery receipt, or rights/ADR/main promotion change.
