# Implementation and parity contract (proposed, 2026-11-15)

## Evidence and scope

Source baseline: [Runner c925816d](https://github.com/Lamy210/SchneeRunner/tree/c925816d4f7ec4e07a5c6db74fd6038fea3aa71d) (SwiftPM, macOS 14+); destination baseline: [Bar ce6478f7](https://github.com/Lamy210/SchneeBar/tree/ce6478f7e64371fdb1a23d826d3292029e100aa2) (Tuist, macOS 15+, existing status item, CPU widget and visual harness). Static source inspection only; not a build, license grant, real-Mac test or ADR acceptance. Record refreshed SHAs and changes before each implementation slice. This contract refines ADR-0004 and existing migration/notification/local-event contracts; their safety restrictions take precedence. No source copying until maintainer records reuse rights (including tests and assets); independently implement documented behavior if reuse is not authorized. No bundled fan artwork without separate clearance.

## Dependency boundaries and ownership

Proposed names (adjust to existing convention without changing direction): SchneeBarCompanionCore (pure state/animation policy), SchneeBarCompanionAssets (bounded filesystem and ImageIO adapter), SchneeBarCompanionFeature (SwiftUI using DesignSystem), SchneeBarProductivityCore (pure deadlines/recurrence), SchneeBarProductivityFeature (SwiftUI), platform adapters owned by SchneeBarApp. Core targets must not import AppKit, SwiftUI, UserNotifications, GitHub, Keychain or HTTP; image decoding is an adapter, not assumed pure because RunnerCore includes platform image processing. App composition owns lifecycle and dependency injection; no dependency from GitHub to Companion or inverse to privileged GitHub services. Shared CPU port belongs to system provider; no direct Mach access in Companion. Add separate target/test dependencies in Project.swift; do not add RunnerApp executable as dependency, submodule or floating branch. No new mandatory server.

## Explicit behavior compatibility and deviations

Runner priority values metric=100, systemAdvisory=300, systemEvent=400, event=500, manual=1000; same-priority most recent generation wins; empty engine defaults to run. Preserve state and playback-rate separation, authored frame timing ratios, manual rate choices 0.5/0.67/1/1.5/2, Automatic clears only manual override, no restart when resolved clip is unchanged. CPU smoothing and hysteresis use original fixtures; do not infer thresholds from approximate README text. New GitHub reaction kind/severity mapping requires explicit fixture and #368/#369 acceptance, not arbitrary elevation above manual. Per-source generation invalidates stale expiry; late event cannot clear a renewed trigger. Local event policy deliberately differs: bounded lease and admission as defined in local-events-and-time-contract.md (legacy no-TTL is not infinite).
Runner v1 distributed notification names are com.schneerunner.character-state-event.v1 and com.schneerunner.build-event.v1. Both are untrusted; build payload has phase only, no build ID. No promise of concurrent build correlation or sender authenticity with v1. Legacy listener off by default, explicit coexistence warning (both apps may react visually); v1 CLI remains Runner-owned, no automatic overwrite of binaries or PATH. If a namespaced Bar CLI/v2 correlation protocol is needed, separate proposal. Build start dash, success sprint 2s, failure idle 5s, cancel clears; a missing terminal expires per existing 1800s lease. Never treat events as shell instructions.
Desktop auto movement starts disabled each launch (source README); clamp restored frame to visible displays, click-through must have a reachable way to disable in Bar settings, no forced accessibility/screen recording permission for cosmetic functions. One status item still clickable with character hidden/invalid. A hidden menu renderer must stop its own work even when desktop renderer is enabled; both off stops frame scheduling and asset decoding.

## CPU service rollout (issue #365)

Bar CPUWidgetProvider already coalesces in-flight sampling and bootstraps at 500ms; descriptor nominal interval 5s. Preserve current behavior when Companion off. First slice shares existing cadence rather than adding a second poller. Faster animation input is a proposal only after measurement; if accepted use one sampling owner and separate consumer publication cadence with nonoverlapping counter-delta semantics. Distinguish invalid/first/sleep samples from true 0%; generation checked after each await. On final unsubscribe cancel acquisition and reset baseline; resume may not publish stale cached data. Widget and animation each consume typed sample with timestamp/generation and explicit validity, EMA lives in policy. Test parallel refresh, unsubscribe during bootstrap, sleep/wake, counter stall/regression, re-enable, raw widget vs smoothed character. No promises about OS-level whole-machine equality without aligned windows.

## UI contract and settings

Retain existing PopoverRootView navigation, including activity detail and delivery history return paths, settings and quit. Add Focus and Character entry points without breaking existing paths. Minimal/Dashboard/Companion are presentation layouts; never grant credentials, turn on legacy event bridge, imported notifications, desktop movement or GitHub reactions implicitly. New flags off initially; independent menu/desktop visibility and safe static fallback. Focus can run without Companion/GitHub; disabling the Focus surface hides presentation but MUST NOT silently cancel native running schedules; separate explicit stop/delete actions. Display active schedules and notification capability in settings even if feature surface hidden. Reduced motion and accessible keyboard/VoiceOver affordances remain. Use SchneeBarDesignSystem tokens, fixture-only visual harness; no snapshot from live user files/tokens. Test Japanese/English text truncation and menu bar width; existing Dev navigation and widget controls must remain reachable.

## Performance and operational verification

Use same Mac/OS, release-like build, power mode and display, 5-minute warmup and 15-minute steady measurement per configuration, three repeats (proposed protocol): Bar baseline, Runner baseline, both separately, integrated disabled, widget+menu, desktop, active Focus, synthetic local storm; offline and GitHub polling runs separately. Record per-process CPU denominator, RSS, wakeups, frame count, acquisition count, launch-to-visible and P95 UI action latency, sample errors, notification reconciliation counts. Provisional absolute targets in docs/SCHNEERUNNER_INTEGRATION.md remain provisional, not measured facts. Proposed regression gate for disabled integration: median CPU <= baseline+0.5 percentage points, RSS <= baseline+20 MiB, wakeups <= baseline+10% or +1/s whichever larger, launch P95 <= baseline+200ms; revise only with documented approved measurement rationale before activation. Zero extra acquisition when no consumer, one counter read per scheduled acquisition (bootstrap pair accounted separately), zero GitHub mutation via adversarial input, zero migrated notification registration. Record results and sample size; do not assert those numbers today. Failure: feature flag off, revert focused PR, preserve credentials and source data, no release/archival.
